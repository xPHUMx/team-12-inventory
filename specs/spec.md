# Spec: ฟีเจอร์แจ้งเตือนสต็อกต่ำ และรายงานมูลค่าสต็อก

## 1. เป้าหมาย (Goal)
เพิ่มความสามารถให้ระบบ Inventory แจ้งเตือนผู้จัดการเมื่อสินค้าใดต่ำกว่า threshold ที่กำหนดผ่านช่องทาง Email และ SMS (จำลองด้วยการ print) และให้ผู้จัดการสามารถดูรายงานมูลค่าสต็อกรวมแยกตามหมวดหมู่สินค้าได้อย่างถูกต้อง

## 2. User Story
| รหัส | User Story |
|---|---|
| US-01 | As a พนักงานคลังสินค้า, I want บันทึกการรับ/จ่ายสินค้าพร้อมอัปเดตสต็อกทันที, so that สต็อกในระบบสะท้อนจำนวนจริง |
| US-02 | As a ผู้จัดการ, I want รับการแจ้งเตือนทันทีเมื่อสินค้าใดต่ำกว่า threshold, so that สั่งซื้อได้ก่อนของหมด |
| US-03 | As a ผู้จัดการ, I want ดูมูลค่ารวมของสต็อกแยกตามหมวดหมู่, so that ตัดสินใจด้านการเงินและจัดงบประมาณได้ถูกต้อง |
| US-04 | As a ผู้จัดการ, I want ตั้งค่า threshold เตือนสต็อกต่ำแยกรายสินค้าได้, so that เหมาะสมกับอัตราการใช้งานของสินค้าแต่ละชนิด |
| US-05 | As a ผู้จัดการ, I want เลือกหรือเพิ่มช่องทางการแจ้งเตือน (Email/SMS), so that ได้รับข้อมูลผ่านช่องทางที่สะดวก |

## 3. Acceptance Criteria (Given-When-Then)

### US-01: บันทึกการรับ/จ่ายสินค้า
```gherkin
Scenario: รับสินค้าเข้าสต็อกสำเร็จ
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร
  When พนักงานบันทึกรับเข้า 30 เมตร
  Then สต็อกคงเหลือกลายเป็น 50 เมตร และบันทึกประวัติสำเร็จ

Scenario: จ่ายสินค้าเมื่อมีสต็อกเพียงพอ
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 50 เมตร
  When พนักงานบันทึกจ่ายออก 20 เมตร
  Then สต็อกคงเหลือกลายเป็น 30 เมตร

Scenario: จ่ายสินค้าเมื่อสต็อกไม่เพียงพอ (Edge case)
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 10 เมตร
  When พนักงานพยายามบันทึกจ่ายออก 15 เมตร
  Then ระบบปฏิเสธการทำรายการ แสดงข้อผิดพลาดว่าสต็อกไม่พอ และสต็อกคงเดิมที่ 10 เมตร
```

### US-02: แจ้งเตือนสต็อกต่ำ
```gherkin
Scenario: จ่ายสินค้าจนสต็อกต่ำกว่า threshold (< threshold)
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 8 เมตร (คงเหลือ 12 เมตร ซึ่งน้อยกว่า 15)
  Then สต็อกคงเหลือ 12 เมตร
  And ระบบส่งการแจ้งเตือนถึงผู้จัดการว่าสต็อกต่ำ

Scenario: จ่ายสินค้าโดยสต็อกยังสูงกว่า threshold
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 50 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 10 เมตร (คงเหลือ 40 เมตร)
  Then สต็อกคงเหลือ 40 เมตร
  And ระบบไม่ส่งการแจ้งเตือน

Scenario: จ่ายสินค้าจนสต็อกเท่ากับ threshold พอดี (Edge case)
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 5 เมตร (คงเหลือ 15 เมตร เท่ากับ threshold พอดี)
  Then สต็อกคงเหลือ 15 เมตร
  And ระบบไม่ส่งการแจ้งเตือน (แจ้งเตือนเฉพาะเมื่อคงเหลือ < threshold)
```

### US-03: รายงานมูลค่าสต็อกแยกตามหมวดหมู่
```gherkin
Scenario: คำนวณมูลค่าสต็อกในแต่ละหมวดหมู่
  Given หมวดหมู่ "ไฟฟ้า" มีสินค้า "สายไฟ" (คงเหลือ 10 เมตร ราคาชิ้นละ 50 บาท) และ "เบรกเกอร์" (คงเหลือ 5 ตัว ราคาตัวละ 200 บาท)
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อกแยกหมวดหมู่
  Then ระบบแสดงมูลค่ารวมหมวด "ไฟฟ้า" เท่ากับ 1,500 บาท

Scenario: หมวดหมู่ที่ยังไม่มีสินค้า
  Given มีหมวดหมู่ "เครื่องมือกล" แต่ยังไม่มีสินค้าในหมวดหมู่นี้
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อก
  Then ระบบแสดงมูลค่ารวมหมวด "เครื่องมือกล" เท่ากับ 0 บาท และไม่เกิดข้อผิดพลาด
```

### US-04: กำหนดค่า threshold แยกรายสินค้า
```gherkin
Scenario: แก้ไขค่า threshold ของสินค้าสำเร็จ
  Given สินค้า "ท่อ PVC" มีค่า threshold เริ่มต้น 10 เส้น
  When ผู้จัดการตั้งค่า threshold ใหม่เป็น 25 เส้น
  Then ค่า threshold ของสินค้านั้นถูกอัปเดตเป็น 25 เส้น
```

### US-05: เลือกช่องทางแจ้งเตือน
```gherkin
Scenario: ส่งแจ้งเตือนผ่านช่องทาง Email และ SMS พร้อมกัน
  Given ระบบลงทะเบียนช่องทางแจ้งเตือน Email และ SMS
  When เกิดเหตุการณ์สต็อกต่ำ
  Then ระบบต้องกระจายแจ้งเตือนไปยังทั้ง Email และ SMS (print ข้อความ [Email] และ [SMS])
```

## 4. In Scope / Out of Scope
- **In Scope:**
  - บันทึกรับ/จ่าย + อัปเดตสต็อกใน Memory
  - ตรวจสอบเงื่อนไขสต็อกต่ำ (Strictly `< threshold`)
  - ระบบแจ้งเตือนหลายช่องทาง Email และ SMS (จำลองด้วยการ print)
  - คำนวณและสรุปรายงานมูลค่าสต็อกรวมแยกตามหมวดหมู่
  - สถาปัตยกรรมแบบ SOLID, Observer Pattern, Factory Pattern, Dependency Injection
- **Out of Scope:**
  - การเชื่อมต่อ SMTP เซิร์ฟเวอร์จริง หรือ SMS Gateway API ภายนอก
  - ระบบ Authentication / Login / สิทธิ์ผู้ใช้งาน
  - ฐานข้อมูล RDBMS ถาวร (ใช้ In-memory structure / Domain Model)

## 5. Functional Requirements (FR)
| รหัส | ความต้องการ | จาก Story |
|---|---|---|
| FR-01 | ระบบต้องอัปเดตสต็อกทันทีหลังบันทึกรับ/จ่าย | US-01 |
| FR-02 | ระบบต้องตรวจสต็อกก่อนจ่าย และปฏิเสธการจ่ายถ้าจำนวนไม่เพียงพอ | US-01 |
| FR-03 | ระบบต้องแจ้งเตือนทันทีเมื่อสต็อกหลังทำรายการต่ำกว่า threshold (`quantity < threshold`) | US-02 |
| FR-04 | ระบบต้องคำนวณมูลค่าสต็อก (`quantity * unit_price`) และรวมยอดตามหมวดหมู่ได้ถูกต้อง | US-03 |
| FR-05 | ระบบต้องรองรับการกำหนด threshold แยกตามแต่ละสินค้า | US-04 |
| FR-06 | ระบบต้องรองรับการเพิ่มหรือเปลี่ยนช่องทางแจ้งเตือนได้โดยไม่กระทบ Business Logic | US-05 |

## 6. Non-Functional Requirements (NFR)
| รหัส | มิติ | ความต้องการ (ต้องวัดได้) |
|---|---|---|
| NFR-01 | Performance | รายงานมูลค่าสต็อก 1,000 รายการ คำนวณและแสดงผลเสร็จภายใน 1 วินาที |
| NFR-02 | Maintainability | สามารถเพิ่มช่องทางแจ้งเตือนใหม่ (เช่น LineNotifier) ได้โดยไม่ต้องแก้ไข `InventoryService` (OCP) |
| NFR-03 | Reliability | ระบบต้องไม่ Crash เมื่อจ่ายสินค้าเกินสต็อก หรือเมื่อหมวดหมู่ไม่มีสินค้า |

## 7. Design Notes
- การแจ้งเตือนต้องแยกออกจาก Business Logic ของการจัดการสต็อกอย่างเด็ดขาด
- ใช้ Observer Pattern เพื่อให้ `InventoryService` ทำหน้าที่เป็น Subject คอยแจ้งเตือน Observers (Notifiers)
- ใช้ Factory Pattern เพื่อสร้าง Notifier ตาม Channel ที่ต้องการ
- ใช้ Dependency Injection ในการส่ง Notifiers เข้าไปใน Service
